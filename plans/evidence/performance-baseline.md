# Performance baseline evidence, 2026-11-15

Bottleneck report for the first slice of the [performance plan](../expression-performance.md).
It records controlled microbenchmarks and a same-host J rerun. Nothing here is a
new end-to-end performance claim, and no library source changed.

## Host and method

- Apple M1, 8 cores, macOS 26.2, Mojo 1.1.0 (8189361e), `--fp-mode contract=off`.
- Release binaries built with `mojo build`; `mojo run` agreed with them within
  noise on the same cases.
- The host was **not quiet**: load average 2.1–6.4, with other applications
  using roughly 45% of a core each. Comparisons are back-to-back in one process
  on one host; absolute values are not portable and are not a quiet-host record.
- Reference: pinned J 9.6.3 build 96 archive, same host, same session, through
  `pixi run compare-j --fetch-j --output build/reference/results-m1.json`.
  33/33 conformance expectations passed; all nine benchmark outputs agreed in
  value, shape and dtype.
- End-to-end numbers are harness medians per API call, including allocation and
  destruction, excluding compilation, process startup and input construction.
- Probe numbers are the mean of 200 timed calls per case after one warm-up,
  with the first cell of each result consumed into a printed sink.

## End-to-end comparison (medians)

| Workload | Elements | Mojj | J | Mojj / J | Mojj ns/element |
| --- | ---: | ---: | ---: | ---: | ---: |
| double `+:` | 1,000 | 7.73 µs | 0.45 µs | 17.1× | 7.73 |
| double `+:` | 10,000 | 75.6 µs | 2.88 µs | 26.3× | 7.56 |
| double `+:` | 100,000 | 765 µs | 20.4 µs | 37.5× | 7.65 |
| sum `+/` | 1,000 | 15.7 µs | 0.40 µs | 39.6× | 15.7 |
| sum `+/` | 10,000 | 156 µs | 0.88 µs | 177× | 15.7 |
| sum `+/` | 100,000 | 1,614 µs | 11.0 µs | 147× | 16.1 |
| RMS | 1,000 | 23.9 µs | 0.67 µs | 35.9× | 23.9 |
| RMS | 10,000 | 232 µs | 4.74 µs | 48.9× | 23.2 |
| RMS | 100,000 | 2,284 µs | 34.9 µs | 65.4× | 22.8 |

Mojj's cost is flat per element across sizes, so the gap is a per-element tax,
not fixed call overhead. J's 1,000-element rows carry most of its per-call
overhead, which is why the 10,000-element ratios are the largest.

Reading: the typed loop is 10–13× faster than the map path and 16–23× faster
than the reduction path. The remaining digit-level detail is that the fold floor
equals a bare dependent-add chain, which is a hardware limit for a strict fold,
not an implementation defect.

## Reduction order in J

Pinned J, full precision output (`9!:11 ] 17`), generated by
`probes/reduction_order.py`:

Every row below reported J storage dtype 8 (Float64); the script asserts and
prints `3!:0` so integer-demoted literals cannot be mistaken for float evidence.

| Input | J `+/` | strict right fold | strict left fold | pairwise |
| --- | ---: | ---: | ---: | ---: |
| `1 1e16 _1e16 1` | 0 | 1 | 1 | 0 |
| 100,000 symbols of `1e16 1 _1e16 1` | 50,000 (exact) | 0 | 1 | 0 |
| 99,999 ones with a leading `1e16` | 1.0000000000096874e16 | 1e16 | 1.00000000001e16 | 1.0000000000099998e16 |
| 99,999 ones with a trailing `1e16` | 1.0000000000099998e16 | 1e16 | 1e16 | 1.0000000000099998e16 |

J matches pairwise accumulation on the four-element vector and matches neither
strict fold on any 100,000-element row. It even recovers the small addends
exactly in the 25,000-block case, where both strict folds lose them, while
remaining inexact by about 3,125 in the leading-`1e16` case against the
correctly rounded exact sum. J's float `+/` therefore reassociates with an
implementation-dependent blocking scheme. No single strict or pairwise model
reproduces all four rows, so a Mojj implementation cannot be validated against
J's rounding, only against its own documented order.

This is why a strict-fold implementation cannot match J's sum timings, and why
changing the order is a documented semantic decision rather than tuning.

## Reproduce

The planning checkout has no Pixi environment, so run the probes from the
implementation checkout (the `main` worktree) with the probe sources copied into
its ignored `build/` directory:

```sh
cd /path/to/mojj              # implementation checkout
mkdir -p build/perf-probes
cp /path/to/mojj-planning/plans/evidence/probes/*.mojo build/perf-probes/

pixi install --locked
pixi run test                                        # suite baseline
pixi run compare-j --fetch-j --output build/reference/results-m1.json

pixi run mojo build --fp-mode contract=off -I src \
  build/perf-probes/api_attribution.mojo -o build/perf-probes/api-attribution
./build/perf-probes/api-attribution

pixi run mojo build --fp-mode contract=off -I src \
  build/perf-probes/loop_floor.mojo -o build/perf-probes/loop-floor
./build/perf-probes/loop-floor

pixi run mojo build --fp-mode contract=off -I src \
  build/perf-probes/simd_map.mojo -o build/perf-probes/simd-map
./build/perf-probes/simd-map

# also from the implementation checkout; needs the pinned runtime above
python3 /path/to/mojj-planning/plans/evidence/probes/reduction_order.py
```

The probe programs write only to stdout; the reduction-order script writes one
temporary J script under `build/`. They are diagnostics, not tests; nothing in
`pixi run test` depends on J or on these timings.

## Limits

No profiler, allocation counter or assembly audit was run, so the split between
`Noun` construction, error-union plumbing and generic-dispatch checks inside the
23 ns/element figure is inferred from the controlled variants, not measured
directly. Values are from one loaded M1 host; the J comparison was reproduced
once on this host and once earlier on an M4, and the ratio direction agreed.
Linux, CI and quiet-host results do not exist. Elementwise SIMD measurements
cover only Float64 on this CPU.
